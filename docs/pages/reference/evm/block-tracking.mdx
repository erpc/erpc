# Block tracking & served tip

Every upstream sees the chain at a slightly different block. Without coordination, routing a request to the one node that is a block behind causes silent "block not found" failures. eRPC polls every upstream continuously and advertises one **served tip** per axis (`latest`, `finalized`): the highest block at least `servedTip.quorum` (default 2) eligible upstreams already have.

**What you get**

- Chain head and finality tracked per upstream, refreshed automatically at the right cadence for each chain's block time
- One rule for every config: a block is served only once a quorum of upstreams has it — a lone far-ahead or wrong-chain node never defines `latest`
- Stalled heads benched automatically, so one frozen node cannot hold `latest` back
- Optional per-group guarantee so the advertised tip stays servable by the upstreams your consensus policy requires
- Per-upstream lag gauges that feed selection policies so slow nodes are deprioritized before requests reach them
- Redis-backed counters share heads across replicas; each replica samples latest-block timestamps on its own debounce schedule.

### How it works

Each upstream gets its own `EvmStatePoller` background goroutine. On each tick of `statePollerInterval` (default 30 s), three concurrent goroutines fetch the latest block, finalized block, and syncing state. A synchronous `Poll()` runs once at bootstrap time to seed the upstream before any request traffic arrives.

Remote head updates do not postpone local latest-block sampling. A local fetch can attach a missing timestamp to the same block already received from a peer. The block-time estimator accepts that matched observation without advancing the head again. Latest-block polling cost scales with replica count.

**Routing the `safe` tag.** On op-stack chains, `safe` is node-relative because each verifier chooses its own L1 confirmation depth. If providers in one pool use different depths, they can honestly return different blocks for the same tag. Set `evm.safeBlockSource` to an upstream id/tag selector when one pool should define that answer:

```yaml
networks:
  - architecture: evm
    evm:
      chainId: 8453
      safeBlockSource: "tier:trusted"

upstreams:
  - id: node-a
    tags: ["tier:trusted"]
  - id: node-b
    tags: ["tier:trusted"]
  - id: provider-a
```

eRPC keeps the `safe` tag verbatim and routes standard block-tagged JSON-RPC requests only to matching upstreams, so the selected pool defines both block height and hash. Cache reads are skipped because an older entry may have been produced by a different source. Operator routing overrides client `use-upstream`; retry and consensus still run inside the selected JSON-RPC pool, so configure participant thresholds accordingly. `eth_query*` and direct gRPC Query APIs retain their existing behavior and are outside this option's scope. If no source is configured or inherited, routing is unchanged. If trusted sources are unavailable, prefer `finalized` for a provider-independent answer.

**Debounce resolution.** To avoid redundant RPC calls, each fetch is gated by `resolveDebounce()`, which picks the first applicable value from:
1. `upstream.evm.statePollerDebounce` — hard per-upstream override; short-circuits all other steps.
2. `tracker.GetNetworkBlockTime × dynamicBlockTimeDebounceMultiplier` (default 0.7) — EMA-derived; active after ≥3 samples.
3. `network.evm.fallbackStatePollerDebounce` (default 5 s) — used while EMA warms up.
4. Hard 1 s floor — applies only if both step 2 and 3 yield zero.

On a 12 s Ethereum Mainnet chain this yields ~8.4 s debounce — fresh enough to catch every block, conservative enough that concurrent pollers share one actual RPC call per window. In Redis-backed multi-pod deployments, the shared counter coalesces fetches across replicas too.

**Finalized debounce.** The finalized fetch widens that debounce to `(latest − finalized) × EMA block time × finalizedDebounceDepthMultiplier` (default 0.05) when this is longer, using the upstream's own latest and finalized blocks. Finalized advances once per finality window, so polling it at the latest-block cadence mostly returns the number already held. With the default the finalized block trails by at most about 5% of the window: ~43 s on Ethereum Mainnet (~72 blocks × 12 s), ~45 s on an Arbitrum-style L2 with a 15 min window. An upstream behind the network's corroborated finalized block (second-highest across upstreams) keeps the regular debounce until it catches up: once a peer sees the next finalized block, the others sample it at the regular cadence. This also covers vendors whose load balancer mixes stale and fresh backends. Chains with near-instant finality (depth of a few blocks) keep the regular debounce. Unknown finalized, latest at or below finalized, or a cold EMA also keep it. Source: <SourceLink file="architecture/evm/evm_state_poller.go" lines="449-471" />

**Dynamic block-time EMA.** The EMA (`alpha = 0.1`, ~19-sample effective window) lives in `health.Tracker` and updates whenever the corroborated network-level latest block advances, using the on-chain timestamp of the upstream report that holds that head (each upstream's latest timestamp is stored beside its head, so the sample comes from whichever poller reported the block). All head publication for a network is serialized under one per-network lock, so a slow re-derivation can never overwrite a newer one. On fast chains where consecutive blocks share the same integer second, block gaps accumulate and samples are normalized. The EMA is not published until ≥3 samples are collected (requiring 4 total advances, because the first stores the baseline without incrementing the sample counter). Values outside `[10 ms, 120 s]` are rejected and reset to the last valid value to prevent runaway spikes after a chain halt. Consumers receive 0 until warm-up completes.

**Per-upstream block counters.** Both `latestBlockShared` and `finalizedBlockShared` are forward-only shared counters: `TryUpdate` rejects values ≤ the current value. A value that would regress more than 1024 blocks fires an `OnLargeRollback` callback and records `erpc_upstream_block_head_large_rollback`.

**Network head and `blockHeadLag` / `finalizationLag`.** The tracker's network-level latest and finalized heads are *corroborated*: the second-highest head across the non-benched reporting upstreams, or the only head while a single one has reported (the same order statistic as the served tip's default quorum). When every reporter is benched it falls back to all of them. One upstream can therefore never move the reference every other upstream is measured against — a lone far-ahead report (an endpoint answering for another chain, a corrupted response) is not corroborated, and a benched (stalled) upstream cannot hold the head back. With exactly two reporters the head is the lower one, so a lone high report and a lone stale report are indistinguishable there; per-upstream block-availability checks still gate block-specific requests. The reporting set is every upstream that has reported a latest or finalized head to the tracker. `blockHeadLag = max(0, network_latest − upstream_latest)`; `finalizationLag = max(0, network_finalized − upstream_finalized)`. Both are recomputed on every `SetLatestBlockNumber` / `SetFinalizedBlockNumber` call and exposed as Prometheus gauges; the raw per-upstream `erpc_upstream_latest_block_number` still shows an outlier's own report. These drive selection-policy predicates such as `blockNumberLagAbove`. Source: <SourceLink file="health/tracker.go" lines="1411-1444" />

**Served tip: the one rule.** Both axes, every config. `EvmHighestLatestBlockNumber` / `EvmHighestFinalizedBlockNumber` build a ballot (`evmTipBallot`) from the upstreams that are:

1. eligible under the selection policy (all registered upstreams until the policy's first decision), narrowed to the request's `use-upstream` selector when present;
2. not syncing per `eth_syncing`;
3. live: a head above 0 that is not a static `blockAvailability.upper.exactBlock` cap the chain has passed (`latestBlockMinus` upstreams are live and vote);
4. not benched (see below).

`PickServedTip` then serves the highest block at least `servedTip.quorum` of them already have: the q-th highest head, or the lowest when fewer than q vote. Fallbacks: with no non-benched live voter, benched live voters vote; with no live voter at all, the static caps vote. The pick then passes, in order, the regression guard, the guarantee floors, and (network-wide `latest` only) the WebSocket delivered-head floor. Nothing is persisted or predicted. Every evaluation for the network-wide pick or a named lane sets the `erpc_network_served_tip_*` gauges, with or without a `servedTip` block. Source: <SourceLink file="erpc/networks.go" lines="464-536" />, <SourceLink file="common/served_tip.go" lines="136-180" />

**Quorum.** `servedTip.quorum` is an integer ≥ 1 or `"majority"` (`floor(N/2)+1` of N voters); unset = 2. It is capped at N. Any other value fails config load. Which head is served (heads sorted descending):

| Voters N | `quorum: 2` (default) | `quorum: majority` | `quorum: 1` |
|---|---|---|---|
| 1 | 1st | 1st | 1st |
| 2 | 2nd | 2nd | 1st |
| 3 | 2nd | 2nd | 1st |
| 4 | 2nd | 3rd | 1st |
| 5 | 2nd | 3rd | 1st |

`quorum: 1` serves the highest head, so a single upstream defines `latest`. A higher quorum trades freshness for servability: more upstreams already have the advertised block. Source: <SourceLink file="common/served_tip.go" lines="50-70" />

**Benching.** The health tracker re-evaluates every reporter on each latest-head report (`evaluateHeadBench`). An upstream is *behind* while a non-benched peer proves the chain went on without it:

- **By height:** a peer that moved after the upstream last moved is higher by no more than a plausible lead: 1024 blocks plus twice the blocks the chain produced since the upstream's head was current (by its last change and its head timestamp). Chain progress uses the network block time, else the peer's own, so a process that starts mid-stall still sees the stall. One such peer is enough. Each move of the upstream resets this rule.
- **By staleness:** a peer that moved within its own or the upstream's stall window is higher within the plausible lead, and its newest block (never counted as newer than now) is at least the stall window younger than the upstream's head block. This holds while the upstream moves, so it catches a node replaying far behind the tip: after a restore, a restart or a deep rollback. One such peer is enough. Only the upstream's own head timestamp proves it stale: a head stored without one (a peer pod's poll through shared state) keeps the last verdict only while a live peer stays a stall window of blocks ahead. A node at the tip has a head block as young as any honest peer's, so a node that trails by less than the stall window of chain time is never benched.
- **By block age:** a peer that moved after the upstream last moved has a newest block at least the stall window younger than the upstream's head block, whatever the heights. This catches a head frozen above a chain that restarted lower (a dead fork), a static far-ahead head, and an endpoint that serves another, slower chain under the same chain id. It takes two such peers while two exist.

Behind without a break for its stall window, `max(30s, 3 × max(statePollerInterval, statePollerDebounce or the block time))`, it is benched: it leaves both served-tip ballots and the lag reference, and `eth_blockNumber` refreshes skip it. Its `blockHeadLag` keeps growing so `blockNumberLagAbove` routes around it: while its head has not moved since the bench, the head counts as no higher than the network head at the bench (a head frozen above a dead fork lags by what the network made since, even after the network passes its height); once it moves again, it lags by its real distance. It rejoins once it has moved since being benched (a move in the evaluation that benched it does not count), no rule above still proves it behind, and its head reached the corroborated non-benched head (second-highest, or the only one); or when no non-benched peer has a head. A voter at or above that head never lowers `latest`, and a lone far-ahead head cannot keep it out. A bench or rejoin also re-derives the finalized lag reference. Stall windows run on the monotonic clock, so a wall-clock step benches nobody. Each bench increments `erpc_upstream_head_benched_total{reason="behind"}` and logs a WARN. Bench state is per process. Source: <SourceLink file="health/tracker.go" lines="1466-1641" />

- **Nobody is benched** for a chain halt itself (no peer moves; a node already a stall window behind when the chain halted is benched like any trailing node), by a moving wrong-chain head above (its lead is implausible), or by one wrong-chain peer whose blocks are younger (the block-age rule needs two).
- **Boundary:** a node that trails by less than the stall window of chain time (for example, 1-3 blocks on a 2s chain) is never benched. It votes with its lower head, which holds the pick back only when it is needed for the quorum (N=2 with the default quorum). `quorum: 1` serves the highest head instead.
- **Boundary:** eRPC compares heights and block times, never block hashes, so it cannot tell a live fork from the canonical chain. During a halt, a node that moves within the plausible lead benches the halted ones after their stall window, and then defines `latest` alone. A benched dead-fork node that starts producing blocks again rejoins once its head reaches the corroborated head.
- **Boundary:** the block-age rule cannot tell two heads frozen above one moving peer (a dead fork the minority left) from two halted honest nodes and one wrong-chain peer. It keeps the frozen pair, so a dead fork that most upstreams stayed on still defines `latest`.
- **Boundary:** two chains under one chain id (an endpoint pointed at the wrong chain) differ by far more than any plausible lead, so only block age tells them apart. Until the slower chain goes twice its stall window without a block, quorum 2 over the pair serves the lower head; then the slower chain is benched, right or wrong. A wrong chain that makes blocks more often than that is never benched. Exclude such an endpoint in config.
- **Boundary:** benching a voter that sat between the pick and a slower voter lowers `latest` to that slower voter's head, as any upstream leaving the ballot does. The regression guard holds only drops beyond `maxRegressionBlocks`.
- **Boundary:** a `latestBlockMinus: N` upstream rejoins on its raw head but votes N below it, so its rejoin can lower `latest` by up to N.
- **Boundary:** rejoin needs the benched head to reach the bar at one report. A node that always trails the second-highest head by a block or two rejoins late; until then it serves traffic while its lag stays under the policy threshold, but does not vote.
- **Boundary:** a bench changes the ballots at once, but routing leaves the benched upstream at the selection policy's next evaluation (`evalInterval`, 15s by default). Until then a request for the new `latest` can reach it; without a configured availability bound nothing gates it, so its missing-data error is retried on another upstream.

**Regression guard (`maxRegressionBlocks`).** When a pick falls more than `maxRegressionBlocks` (0 = 1024) below the corroborated evidence — the second-highest live head, or the last live-corroborated pick — the network serves its last corroborated pick instead, never above the highest live head. It holds for at most 1 minute, then fails open and serves the pick as computed. In-process only; selectors without a lane get no guard; `-1` disables it. Each transition increments `erpc_network_served_tip_regression_total` (`outcome="held"` or `"failed_open"`). Source: <SourceLink file="erpc/networks.go" lines="1034-1173" />

**WebSocket delivered-head floor.** Network-wide `latest` (no `use-upstream`) is lifted to the highest head already delivered to a `newHeads` subscriber by this instance, or by any instance through the shared counter `network/<project>/<network>/latestBlock`. The floor applies only within `maxRetryableBlockDistance` of the freshest live head (or when no head is known), and never lifts `latest` past a guarantee floor. Source: <SourceLink file="erpc/networks.go" lines="1464-1492" />

**`eth_blockNumber`.** With `enforceHighestBlock` on (the default) and the served head known, eRPC answers `eth_blockNumber` from the served head without dispatching, scoped to the request's `use-upstream` selector. Each answer triggers `EvmRefreshLatestBlock`: in routing order, the pollers of quorum-many voting (non-syncing, non-benched) upstreams refresh in the background, each only when its stored head is older than its poll debounce, one refresh in flight per poller. The answer is the head as of the last refresh, so a client that alone polls every N seconds reads a head up to N seconds old (never older than `statePollerInterval`, and fresher when other traffic refreshes it); a request that follows it sees the refreshed head, so `eth_call` "latest" never runs below the `eth_blockNumber` a client just read. With the head unknown (cold pollers) the request is forwarded. Every response that reaches the post-forward hook — an upstream answer or a cache hit — is pinned exactly to the served head when it is known: higher values are lowered, lower values are raised. `enforce-highest-block=false` forwards and returns the upstream's answer unchanged. Source: <SourceLink file="architecture/evm/eth_blockNumber.go" lines="13-39" />, <SourceLink file="erpc/networks.go" lines="838-891" />

**Guarantee subsets (`guaranteedMethods`, `guaranteedFor`).** After the pick, the advertised tip is clamped down to the lowest majority of every configured guarantee subset, so it is never a block a required subset cannot serve. `guaranteedMethods` names a subset by method support; `guaranteedFor` names one by upstream id/tag selector — the same vocabulary as `use-upstream` and `consensus.requiredParticipants`. Both run through the same ballot rule (`evmTipBallot`, with `quorum: majority` whatever the network quorum) and the same min-across-subsets fold in `guaranteedFloor`; only the membership predicate differs. Each subset is clamped to its OWN MAJORITY, never its minimum, so a single frozen member is outvoted inside its group. An empty or unmatched subset constrains nothing (the tip is never pinned to 0), and the clamp can only lower the tip — a group ahead of the network pick never raises it. Source: <SourceLink file="erpc/networks.go" lines="1494-1607" />

**Selector-scoped served tip.** When a `use-upstream` selector is present, `tipCandidateUpstreams` narrows the ballot to the matching upstreams; the pick is the same rule over that subset. A "simple group selector" is a single glob pattern (optionally negated with `!` at position 0), containing no whitespace or `()|&,` characters, of length ≤128, that matches 2–(N−1) upstreams. For such selectors, a per-group `servedTipPartition` (a *lane*) is lazily materialized: `partitionKeyFor` resolves the matched upstream ID set, sorts it, SHA-256 hashes the sorted `\0`-joined IDs, truncates to 8 bytes, and encodes as hex (key = `"grp:" + hex`). A lane holds no pick state: only its gauge label, advance-age watchdog and regression-guard memory. Equivalent selectors (same matched set) share one lane. Up to 16 lanes are allowed per network; other selectors get the same pick with no gauges and no regression guard. Source: <SourceLink file="erpc/networks.go" lines="685-799" />

**Syncing state machine.** `eth_syncing` is called with a 5 s sub-context on each tick. The upstream is declared fully synced only after 4 consecutive "not syncing" responses (`synced counter ≥ 4`); any syncing response resets the counter to 1. The non-standard `{Ok: bool}` response shape is supported: `Ok=false` is treated as still-syncing. After 10 consecutive failures with no prior success, `skipSyncingCheck` is set permanently and the state is fixed at `Unknown` for the process lifetime. If `upstreams[*].evm.skipSyncingCheck: true` is set in config, `eth_syncing` is never called at all and the state is immediately fixed at `NotSyncing` — use this for nodes that always return a syncing object regardless of actual sync status.

**Skip-on-failure semantics.** Both `skipLatestBlockCheck` and `skipFinalizedCheck` follow the same pattern: 10 consecutive failures with no prior successful poll sets the skip flag permanently and the poller stops calling that method. Once the upstream has had at least one success (`*SuccessfulOnce = true`), failures are only logged and never trigger the skip. This prevents false-positive disablement during transient degradations. Source: [`architecture/evm/evm_state_poller.go:L420-L445`](https://github.com/erpc/erpc/blob/main/architecture/evm/evm_state_poller.go#L420-L445)

**`IsBlockFinalized` decision tree:**
1. Both `finalizedBlock == 0` and `latestBlock == 0` → `ErrFinalizedBlockUnavailable`.
2. `finalizedBlock > 0` → `blockNumber ≤ finalizedBlock`.
3. `finalizedBlock == 0` and `latestBlock > 0` → infer `finalizedBlock = latestBlock − FallbackFinalityDepth` (default 1024) and compare.

**Earliest block detection.** When `blockAvailability.lower.earliestBlockPlus` is configured, `binarySearchEarliest` finds the first block in `[0, latestBlock]` where a probe RPC call returns data. Probe types: `blockHeader` (`eth_getBlockByNumber`), `eventLogs` (`eth_getLogs`, requires ≥1 log entry), `callState` (`eth_getBalance`), `traceData` (tries `trace_block`, `debug_traceBlockByHash`, `trace_replayBlockTransactions` in order). Results are stored in cross-pod shared counters. If `blockAvailability.*.updateRate` is set, a scheduler goroutine re-runs the search at that interval.

#### Removed keys

Strict config loading rejects these keys, so a config that still sets them fails at startup.

| Removed key | Replace with |
|---|---|
| `servedTip.enabledFor: [latest, finalized]` | `servedTip.quorum: majority`. With ≤ 3 voters the default quorum (2) already serves the same block. |
| `servedTip.clusterDelta` | Delete it. |
| `servedTip.trajectoryWindow` | Delete it. Benching replaces the trajectory referee. |
| `enabledFor` containing `latest` turning on `shortCircuitFutureBlocks` | Set `evm.shortCircuitFutureBlocks: true` explicitly. |

### Request/response behavior

- A block-tagged request for `"latest"` / `"finalized"` is interpolated to the served tip, which at least `quorum` voters already have. Routing does not exclude upstreams below it; per-upstream block-availability checks and retries handle a node that lacks the block.
- `ErrFinalizedBlockUnavailable` is retryable (N:yes). Requests are automatically retried on a different upstream. On the wire it maps to HTTP 200 with JSON-RPC error code `-32603`.
- `ErrUpstreamBlockUnavailable` is produced by `CheckBlockRangeAvailability` (used for `eth_getLogs`, `trace_filter`, `arbtrace_filter`) when both block bounds are outside the upstream's availability window. Retryable at the network level.
- `erpc_network_served_tip_block_number` and `erpc_network_served_tip_lag_blocks` are set on every evaluation with a known tip, for every network, with or without a `servedTip` block. [<SourceLink file="erpc/networks.go" lines="1661-1696" />]
- `eth_blockNumber` is answered from the served head without an upstream call while `enforceHighestBlock` is on and the head is known; every response is pinned exactly to that head. See **`eth_blockNumber`** above.
- The `SuggestLatestBlock` fast path (called when a response is observed during request forwarding) is non-blocking and uses no debounce. `SuggestFinalizedBlock` uses `TryLock` and is async — suggestions may be dropped under high concurrency.

### Best practices

- Leave `quorum` at 2 unless interpolated requests often land on an upstream without the block; then use `majority` (or a fixed count) on pools of 4 or more.
- Lower `fallbackStatePollerDebounce` to 200–500 ms on sub-second chains (Arbitrum, Base, Optimism) so warm-up doesn't stall on a 5 s default.
- Use `guaranteedMethods: ["trace_*"]` when mixing archive and non-archive upstreams — prevents the served tip from advancing past what trace-capable nodes have.
- Avoid setting `dynamicBlockTimeDebounceMultiplier: 0`; it is silently ignored and the default 0.7 is used. To impose a fixed debounce, use `statePollerDebounce` on the upstream instead.
- Monitor `erpc_upstream_block_head_lag` per upstream and alert on `erpc_upstream_head_benched_total` increases: a benched upstream stayed behind peers that kept advancing.
- Alert on `erpc_network_served_tip_advance_age_seconds` staying high on a live chain: the served value stopped moving, whatever the cause.
- Alert on any increase of `erpc_network_served_tip_regression_total`: the guard held (or failed open on) a pick far below the live heads.

### Edge cases & gotchas

1. **`statePollerInterval: 0` disables the poller silently.** All block numbers return 0, syncing state is `Unknown`, `IsBlockFinalized` returns `ErrFinalizedBlockUnavailable` immediately, and block availability checks fail-open. The upstream is not excluded from selection but its head is 0, so it never votes.
2. **Two upstreams with the default quorum serve the lower head.** One stalled node holds `latest` until it is benched (its stall window: 90s at the default 30s `statePollerInterval`); then the other votes alone. A node that is catching up slowly is not benched and holds `latest` at its head until `eth_syncing` reports it syncing.
3. **A rogue head needs `quorum − 1` accomplices.** One far-future or wrong-chain head never moves the pick at quorum ≥ 2. `quorum: 1` serves the highest head, rogue included.
4. **`dynamicBlockTimeDebounceMultiplier: 0` is silently treated as unset.** The guard `> 0` causes the value to fall through to the default 0.7.
5. **Static `upper.exactBlock` caps vote only when no live head exists.** A cap the chain has passed is a serving range, not a head observation; it votes only in an all-capped ballot. `latestBlockMinus` upstreams always vote.
6. **Selectors without a lane emit nothing and get no regression guard.** Boolean-expression selectors (`|`, `&`, `(`, `)`, embedded `!`), single-upstream or match-all selectors, and selectors beyond the 16-lane cap get the same pick over their subset, with no gauges and no guard.
7. **Maximum 16 lanes per network.** Equivalent selectors (same matched upstream set) dedup to one lane.
8. **Benching is per process.** Each instance benches from its own in-memory tracker, so pods can disagree on which upstream is benched.
9. **`eventLogs` probe requires ≥1 log entry.** A block with no events returns an empty array, treated as "not available" — the binary search may incorrectly mark data-sparse blocks as unavailable.
10. **`updateRate` goroutine is NOT restarted on config hot-reload.** Only a process restart picks up a changed `updateRate` for `earliestBlockPlus` bounds. Setting `updateRate` alongside `latestBlockMinus` produces a validation warning (not an error); the value is silently ignored at runtime.
11. **`ErrFinalizedBlockUnavailable` is retryable.** It carries no explicit opt-out flag, so `IsRetryableTowardNetwork` returns true. On the wire it maps to HTTP 200 with JSON-RPC error code `-32603`.
12. **Served-tip gauges freeze during a total outage.** With no voter the tip is 0, so `_block_number` and `_lag_blocks` keep their last value. `erpc_network_served_tip_advance_age_seconds` keeps rising; alert on it.
13. **`OnValue` callback passes `blockTimestamp=0` for cross-pod replications.** Only the replica that actually fetches feeds the EMA with a real timestamp; replicas receiving shared-counter updates use `blockTimestamp=0`, so only one pod per network feeds the EMA per debounce window.
14. **`ErrFinalizedBlockUnavailable` never fires if only `latestBlock == 0`.** The error requires BOTH counters to be 0. If the upstream supports `eth_getBlockByNumber("latest")` but not `"finalized"`, `IsBlockFinalized` falls back to `latestBlock − FallbackFinalityDepth` instead of returning the error.
15. **`SuggestFinalizedBlock` may drop updates under load.** It uses `TryLock`; if an update is already in progress the suggestion is discarded. Finalized block updates may lag under high request volume.
16. **`SuggestLatestBlock` monotonic within a process but not across pod restarts.** It calls `TryUpdate` which the shared counter rejects if the value is ≤ current. Across pod restarts the shared counter (Redis) retains the last value, so a restarted upstream reporting a lower block number after a reorg is silently ignored for up to 1024 blocks of rollback.
17. **`eth_syncing` result `{Ok: false}` is interpreted as SYNCING.** The non-standard `{Ok: bool}` response shape is handled by `!Ok`: `Ok=false` means not-ok = still syncing. Source: [`architecture/evm/evm_state_poller.go:L1087-L1100`](https://github.com/erpc/erpc/blob/main/architecture/evm/evm_state_poller.go#L1087-L1100)
18. **`erpc_network_served_tip_lag_blocks` is `Freshest − served`, clamped at 0.** `Freshest` is the second-highest voter, so a lone far-ahead head never inflates it. With quorum ≤ 2 and no guarantee floor it reads 0; it is non-zero only with a higher quorum or a guarantee floor below the pick.
19. **`guaranteedFor` on a ONE-member group lets that upstream set the tip.** The clamp is the group's majority, and a group of one has no majority to outvote a stall — a single frozen member holds the network tip at its head. Naming exactly one upstream is declaring it mandatory; name ≥3 for a group that tolerates one stall. Same property `guaranteedMethods` already has for a method only one upstream supports.
20. **`guaranteedFor` constrains nothing when its group is absent from the eligible set.** If every matching upstream is lag-excluded, cordoned or mid-restart, the group ballot has no inputs and the clamp is skipped rather than pinning the tip to 0. A group whose members are all static serving-range caps floors the tip only when no REGISTERED member is live — the same transient-vs-permanent rule `guaranteedMethods` applies, so an eligibility collapse cannot hand back a frozen cap. Source: <SourceLink file="erpc/networks.go" lines="1609-1659" />
21. **Guarantee floors use `majority` whatever `quorum` says.** A network quorum of 1 still clamps to each guaranteed group's majority.
22. **Finalized block polling is permanently skipped on unsupported chains.** After 10 consecutive `eth_getBlockByNumber("finalized")` failures without any prior success, `skipFinalizedCheck = true`. `IsBlockFinalized` then falls back exclusively to `latestBlock − FallbackFinalityDepth`. On PoW chains or chains without EIP-4895 finality, this is the only reachable path.
23. **Finalized trails by up to `finalizedDebounceDepthMultiplier` of the finality window.** Response finality uses the serving upstream's own finalized block and cache hits the lowest across upstreams, so requests for blocks finalized within that span stay classified unfinalized (cache TTL, finality-scoped policies) until the first upstream polls again; the rest then catch up at the regular debounce. A `finalized` response or `SuggestFinalizedBlock` inside the window still advances it at once.
