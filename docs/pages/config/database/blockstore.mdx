# Blockstore

The live blockstore builds its window of recent verified blocks from what clients
already read. Every recent block or log response eRPC serves, whether from its
response cache or an upstream, is adopted: its header is linked to its neighbours by
parent hash, and a full block body or a complete, unfiltered log list is validated and
shared by block hash through Redis. The next read of the same block, filtered logs
included, on any replica is served from the blockstore with no upstream call. With no
client traffic and no WebSocket subscribers, the blockstore makes no upstream calls at all.

The blockstore follows the chain itself (one header per new block, by one lease holder
per trust fingerprint, namespace, project and network) only while at least one
WebSocket subscriber exists anywhere in the fleet. Its own fetches go through eRPC's
response cache, so a header a client already fetched costs nothing.
Independent EVM state pollers and probes still run per replica and can call upstream.

Historical caching is an independent opt-in for finalized blocks outside that moving
window. It keeps full blocks that clients already received, with a finalized
height-to-hash index guarding canonical reads, and never calls upstream on its own.
Historical entries expire after their configured TTL. Finalized logs have one source:
the logs fill below, whose per-block entries at finalized heights are kept for
`logsFill.finalizedTtl`. This does not change the live window or its
single-refresher fleet coordination.

The cache reuses a Redis connector declared for the [EVM JSON-RPC cache](/config/database/evm-json-rpc-cache).

## Logs fill (small `eth_getLogs` ranges)

`logsFill` is a separate opt-in that cuts upstream `eth_getLogs` calls when many
clients poll the same recent blocks with different `address`/`topics` filters. For an
explicit hex `fromBlock`/`toBlock` range of at most `maxRange` blocks (default 10) at or
below the network head, eRPC makes one unfiltered `eth_getLogs` upstream call for the
range, stores each block's complete log list (including empty blocks), and filters
every request locally. Later requests over those blocks, with any filter, need no
upstream call. A failed or unusable fill falls back to forwarding the original request.

It works without `enabled` or `historical`. With `connectorId` set it shares the Redis
connector, and replicas coordinate so one of them fetches a given range while the others
wait briefly (`peerWait`) for its result; otherwise each replica keeps a bounded
in-memory store.

The tradeoff is response size: an unfiltered range on a busy chain can be much larger
than any filtered answer, which is why `maxRange` stays small. Recent (unfinalized)
blocks are kept for only about one block time.

```yaml
projects:
  - id: main
    networks:
      - architecture: evm
        evm:
          chainId: 1
          blockStore:
            logsFill:
              enabled: true
              # widest fromBlock..toBlock span answered from one unfiltered fill
              maxRange: 10
```

Disabled by default. When disabled, behavior is unchanged.

database:

## Config schema (`projects[].networks[].evm.blockStore`)

Defaults from `EvmBlockStoreConfig.SetDefaults` (<SourceLink file="common/config_blockstore.go" lines="152-187" />), called by `EvmNetworkConfig.SetDefaults` (<SourceLink file="common/defaults.go" lines="2570-2572" />).

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Opt-in. |
| `connectorId` | — (required) | Id of a `driver: redis` connector in `database.evmJsonRpcCache.connectors`. Validated at config load (`ValidateConnector`); a missing or non-redis connector fails setup. Payload `Get`/`Set` and snapshot reads use the configured connector wrapper and its failsafes. Lease operations and token-fenced snapshot publication use the underlying Redis client; the connector owns that client's lifecycle and reconnects. |
| `depth` | `128` (1..4096) | Canonical blocks retained. |
| `maxBytes` | `256MB` | Per-replica in-memory bound for on-demand block bodies and log lists (headers are not counted). Over it, the lowest heights are evicted first; they are reloaded from Redis, not upstream, on the next read. |
| `maxBlockBytes` | `min(16MB, maxBytes)` | A block body or log list larger than this is never cached; reads of it go upstream. |
| `maxPerTick` | `min(16, depth)` (1..depth) | Older headers backfilled per refresh while the window is shorter than `depth` (cold start or recovery). New heads above the window are always fetched in full. |
| `concurrency` | `4` (1..64) | Maximum simultaneous header fetches on the lease holder, and per-height log loads of one live-window or `logsFill` request. |
| `pollInterval` | `2s` | Tick period. Each tick checks whether a WebSocket subscriber exists (locally, or fleet-wide through the Redis presence mark, see edge case 27); only then does the lease holder check the network's in-memory latest block and fetch headers for new heights (a state-poller advance or a new subscription triggers an early tick). An unchanged tip costs no upstream call. Followers check Redis for the shared snapshot. Without subscribers a tick makes no upstream call. |
| `fetchTimeout` | `10s` | Timeout for each header, block or logs fetch. |
| `maxLogsRange` | `depth` | Widest `eth_getLogs` range served from live or historical blockstore data. The network's `evm.getLogsMaxAllowedRange`, `getLogsMaxAllowedAddresses` and `getLogsMaxAllowedTopics` are checked first, so a request the network would reject is never answered from the blockstore. |
| `maxStaleness` | `5 × pollInterval` | Maximum age of the shared canonical snapshot, and of the newest observation confirming an adopted header (edge case 28). Once stale, it cannot authorize an HTTP cache hit and WebSocket subscriptions close. |
| `namespace` | `default` | Deployment isolation prefix. The effective namespace is combined with a SHA-256 fingerprint of the network's upstream set and effective cache settings. |
| `historical.enabled` | `false` | Opt in to an independent cache for finalized full blocks outside the live window, adopted from block responses already served to clients (no upstream call of its own). |
| `historical.ttl` | `1h` | TTL for historical block payloads and finalized height-to-hash index entries. Must be positive when historical caching is enabled. |
| `logsFill.enabled` | `false` | Opt in to the small-range `eth_getLogs` fill. Independent of `enabled` and `historical.enabled`. Defaults from `EvmBlockStoreLogsFillConfig.SetDefaults` (<SourceLink file="common/config_blockstore.go" lines="86-110" />). |
| `logsFill.maxRange` | `10` (1..1000) | Widest `toBlock - fromBlock + 1` handled. Also capped by `evm.getLogsMaxAllowedRange` and the smallest upstream `getLogsAutoSplittingRangeThreshold`. |
| `logsFill.finalizedTtl` | `1h` | TTL of per-block entries at or below the network's finalized height. |
| `logsFill.unfinalizedTtl` | `0` = derived | TTL of per-block entries above the finalized height. `0` uses the network's estimated block time clamped to 2s..12s (2s while unknown). |
| `logsFill.emptyTipGuard` | `2` (>= 1) | An unfinalized block with no logs is stored only when it is at least this many blocks below the network's latest head. |
| `logsFill.memoryMaxBytes` | `64MB` (>= 1MB) | Per-network LRU bound when no `connectorId` is set. |
| `logsFill.peerWait` | `1.5s` (0..1m) | With `connectorId` only: the longest a miss waits for another replica that holds the range's fill lock before fetching itself. `0` disables cross-replica coordination (per-replica singleflight only). Ignored for the in-memory store. |

Historical block entries contain full transactions and do not include logs. The finalized height-to-hash index is checked before an entry can be served, so stored data alone does not authorize a non-canonical answer. Historical logs are not a separate store: `eth_getLogs` at finalized heights is served by `logsFill` entries (edge cases 17-23) or forwarded unchanged.


## What is served

- A height or hash is "in the window" when it is in the fresh followed snapshot (WebSocket subscribers exist) or is a fresh adopted header (edge case 28).
- `eth_getBlockByNumber` with an explicit hex number and boolean flag. `false` is the verified window header itself (no fetch); `true` serves the cached full block, fetching it once on a miss. Tags (`latest`, `finalized`, ...) always go through the normal path; their responses are still adopted.
- `eth_getBlockByHash`, only when the hash is canonical in the current window; same `true`/`false` behavior.
- `eth_getLogs` with `blockHash`, or with hex `fromBlock`/`toBlock` where **every** block of the range is in the current window, and the span is <= `maxLogsRange`. Uncached heights are fetched once by block hash (or through `logsFill`, see edge case 25) and then filtered locally. Only `address`, `topics`, `blockHash`, `fromBlock`, `toBlock` members are accepted (`blockHash` together with `fromBlock`/`toBlock` goes upstream); addresses must be 20-byte and topics 32-byte hex, and topic matching follows geth (a filter with more topic positions than a log never matches it). Anything else goes upstream.
- Requests with `useUpstream`, an integrity selector, `skipCacheRead`, or internal requests bypass the blockstore (they may target a different trust set). Integrity-selector requests also bypass the ordinary JSON-RPC cache and in-flight request multiplexing when the configured integrity module accepts per-request selection (`headerMode: profiles` or `headerMode: full`). Ignored selectors leave ordinary caching and multiplexing enabled.

## Edge cases & gotchas

1. **No partial or unverified answers.** While cold-filling, the lease holder publishes the contiguous newest suffix of verified headers and backfills `maxPerTick` older headers per tick. The snapshot's `incomplete` marker tells a new lease holder to continue the backfill after takeover. Every served payload is checked against the verified window header for its height: a body must match number, hash, parent hash and the header's transaction hashes; a log list must be complete for that header (see 2). A failed or oversized fetch is a miss; HTTP follows normal forwarding. An empty log result is returned only when every block in the range is in the window and none matched. Partial windows never create partial HTTP responses.
2. **Payload validation.** A header must contain a non-null `transactions` array; `[]` is a valid empty block, but an omitted or null field is rejected on the lease holder and on follower reads. A log list is cached only when it is non-null, log identities match the block and its transactions, log indexes strictly increase, no log is removed, and the bloom recomputed from returned logs matches `logsBloom`. Bloom mismatch rejects the record, including an empty response for a nonzero bloom. Bloom equality is not proof of completeness: omitted logs that contribute no new bloom bits can remain undetected. Complete log responses still depend on the configured upstream trust set.
3. **Reorgs.** The tip comes from the network's in-memory latest block (state pollers and response enrichment); `eth_blockNumber` is called through the network only while that value is unknown or has not advanced for `max(3 × block time, 2 × pollInterval)`. When the tip advances, only the new heights' headers are fetched. If the first new header does not link by parent hash to the retained tip, the lease holder walks back one retained header at a time until it links, so a reorg of depth d costs d extra headers. A walk-back past the whole window rebuilds it from the tip and closes subscriptions. A same-height replacement with no new block is detected when an on-demand body fetch returns a different hash for that height (the next tick re-verifies the tip with one header), or when the next block arrives. A lower observed tip is treated as a lagging upstream, even below the retained window: it neither fetches nor truncates headers, closes subscriptions, or extends freshness. The verified view remains available only until its existing `maxStaleness` deadline. Parent mismatch on forward extension or an on-demand hash mismatch provides independent reorg evidence. Bodies and logs cached for an orphaned hash are dropped from memory and never served; a fetch in flight across a reorg is discarded if its hash left the window. Followers consume the published snapshot and its Redis headers rather than checking headers against upstream.
4. **Fleet coordination and trust scope.** A token-fenced Redis lease selects one head-cache refresher per scope: trust fingerprint, configured namespace, project and network. The holder verifies the header window and publishes a snapshot only after every referenced header is present in Redis. A holder whose refresh or publish fails on 3 consecutive ticks releases the lease, so a replica with a broken upstream path cannot keep leadership while publishing nothing; a healthy replica takes over on its next tick. An advancing refresh probes the advertised tip before fetching intermediate heights, so an unavailable tip costs one retry per tick rather than repeatedly fetching the entire forward range. These errors still count toward failover, but the retained window is not reset. On acquisition, including before a replica's first follower tick, the new leader seeds its window from the published snapshot and validated Redis headers. Stale snapshots may seed recovery only, never authorize serving until a successful refresh. Snapshot metadata is retained for `max(record TTL, maxStaleness)` rather than expiring at the serving freshness deadline. Missing, expired or invalid recovery headers fall back to the existing retained window or a bounded cold fill. Followers validate the snapshot and its Redis headers and make no background upstream calls while Redis and the snapshot remain healthy. A body or logs miss on any replica is fetched once fleet-wide (edge case 24). The fingerprint includes upstream/provider configuration, effective network forwarding settings and effective head-cache settings such as `depth` and `maxBytes`; different settings use separate lease and snapshot scopes. This does not stop independent EVM state pollers, probes, or ordinary HTTP misses from reaching upstreams on each replica.
5. **Redis loss or stale state.** With fleet coordination, lease/snapshot errors, a missing or stale snapshot, or a missing/invalid payload required to install a snapshot invalidate the local view. A transient payload transport/read timeout may retain the previous fresh view only when the new snapshot overlaps it, agrees at every overlapping height and is not behind it. The failed tick does not extend freshness or emit partial events; retries must succeed before the previous leader timestamp reaches `maxStaleness`. Missing keys, corrupt payloads, Redis server/data errors and conflicting snapshots still fail closed. A valid `incomplete` snapshot serves its complete suffix, while requests outside that suffix miss. HTTP cache misses proceed through normal forwarding. Redis payloads alone never authorize a hit without a valid snapshot.
6. **Blockstore upstream traffic** (headers on the lease holder while subscribers exist, on-demand bodies and `blockHash` logs on whichever replica misses first) goes through the normal network path (selection policy, failsafe, and the ordinary [EVM JSON-RPC cache](/config/database/evm-json-rpc-cache) read and write, see edge case 30) as internal JSON-RPC requests with explicit IDs. Independent state pollers and probes remain per replica.
7. A header that omits `logsBloom`, or log fields that are non-standard, make that block's logs uncacheable; those reads go upstream. A body or log list over `maxBlockBytes` is never cached; reads of it go upstream, and a `logs` subscription whose new block's logs cannot be loaded closes rather than skip it.
8. **Subscription gaps fail closed.** Backfilling older headers does not close a subscription when its next event remains contiguous with the previous view. Skipped heights, a reorg deeper than the window, or an added block whose logs cannot be loaded for a `logs` subscription close the stream rather than emit a partial event. Clients must reconnect/resubscribe and recover their own missed range.
9. **Connector lifecycle and follower reuse.** Payload `Get`/`Set` and snapshot reads use the configured connector wrapper. The blockstore accesses the underlying Redis client only for lease operations and token-fenced snapshot publication; the connector owns its lifecycle and the blockstore does not close it. Followers validate newly loaded headers, but reuse headers already validated in the local view when their height, hash and parent match the accepted snapshot. Freshness is still bounded by the leader's snapshot timestamp, not by the time the follower reads it. Lease/snapshot errors fail closed; the narrow transient payload-read exception is described in edge case 5.
10. **Exact input semantics.** Addresses require 20-byte hex and topics/hashes require 32-byte hex. A trailing wildcard topic still requires that topic position to exist. Invalid filters, mixed blockHash/range selectors, unknown members and directed requests bypass local answers.
11. **Memory sizing.** Each replica keeps `depth` headers per enabled network (a few KB each) plus on-demand bodies and log lists up to `maxBytes`. `maxBytes` applies per enabled network per replica; the default `256MB` is 256 MiB (`256 << 20`), but it fills only with payloads clients actually read. Budget separately for Go/object overhead, in-flight fetches, other caches, and Redis storage.
12. **Fork compatibility.** Configs written for the unmerged fork branch must replace `mode`/`redis` with `connectorId` and drop `headSource`/`servedTipMaxAge`. Those keys no longer exist.
13. **Store retention.** Redis headers, bodies and logs expire by TTL (`(depth + 16) × 30s`) and may outlive the window. The lease holder rewrites each current header at half its TTL rather than every poll; bodies and logs are written once when fetched. `depth` and `maxBytes` bound local cache use, not total fleet Redis storage. Set Redis `maxmemory` and an eviction policy appropriate for the deployment.
14. **Historical data is independent of the moving live window.** `historical.enabled` defaults to false. Historical-only configurations still require the Redis connector. When enabled, full blocks and a finalized height-to-hash index are kept. Reads are constrained to the current corroborated finalized height and indexed canonical hash. If a fresh live window overlaps the indexed height with a different hash, historical reads miss and delete the stale height index, without an upstream call. Unknown finality, an absent index entry, or an unavailable payload is a miss and follows ordinary cache/upstream fallthrough. Entries expire after `historical.ttl`. Historical logs are not stored here: finalized `eth_getLogs` ranges are answered by `logsFill` (one unfiltered range call per miss, edge case 18) or forwarded unchanged; ranges wider than `logsFill.maxRange` pass through with no extra fetches. It does not alter the live window, freshness, or fleet lease behavior.
15. **Historical traffic remains distinct from live fleet behavior.** The historical cache uses the same configured Redis connector but a separate namespace. It does not make followers into live-window refreshers and does not suppress normal HTTP upstream forwarding when historical data is absent or invalid.
16. **Historical caching never calls upstream.** It only adopts `eth_getBlockByNumber`/`eth_getBlockByHash` responses already served to a client from an upstream (responses replayed from the response cache, directed requests and the blockstore's own fetches are ignored), at heights at or below the finalized height. A by-number response indexes its hash at that height; a full (`true`) response also stores its body under its hash; a by-hash full response stores a body that is served only once its hash is indexed. A by-number response whose hash differs from the indexed one, or from the live window, deletes the index entry (the height misses until observed again) instead of rechecking upstream. Hash-only (`false`) responses never trigger a full-block fetch, and logs responses are never expanded into per-block fetches. Re-adopting a stored block writes nothing.

17. **Logs fill eligibility.** `logsFill` handles only a single filter object with hex `fromBlock`/`toBlock` (`to >= from`), optional `address`/`topics`, no `blockHash`, a span within the effective `maxRange`, and `toBlock` at or below the network's latest head. An unknown head, tags, other members, directed requests (`useUpstream`, integrity selector, any `skipCacheRead` value including connector-ID patterns (an explicit `"false"` does not bypass), internal), split sub-requests, and requests exceeding `getLogsMaxAllowedAddresses`/`getLogsMaxAllowedTopics` take the normal path untouched. Order: live/historical blockstore first, then the logs fill, then the ordinary cache and upstream.
18. **One upstream call per miss.** If any height in the range is missing, the fill makes one unfiltered `eth_getLogs` for the whole requested range through the normal network path (selection, failsafe, retries) with ordinary cache read and write bypassed. Concurrent fills of the same `(from, to)` coalesce into one call per replica (singleflight); followers are served from the same result. With `connectorId` and `peerWait > 0`, replicas also coalesce across the fleet, see edge case 23. The client's filtered request is never also sent upstream unless the fill fails.
19. **Fallback never worsens behavior.** An upstream error, a null/non-array result, a log outside the range, two block hashes at one height, a duplicate `logIndex`, or any `removed: true` log stores nothing and forwards the client's original request as if the fill were disabled.
20. **Reorg safety.** Entries are keyed by height and overwritten by each fill, so a refill after a reorg replaces the old hash. Unfinalized entries live about one block time, so a reorged height can be served stale for at most that long. Heights with logs are self-identifying (they carry `blockHash`); an empty height carries no identity, and a lagging upstream can report a block it has not imported as empty, so unfinalized empty heights within `emptyTipGuard` blocks of the head (sampled before the fetch) are answered but not stored. Finalized heights use `finalizedTtl`.
21. **Response shape.** Results are the upstream's log objects byte-for-byte, ordered by `(blockNumber, logIndex)` ascending; no match is `[]`, never `null`. Address and topic matching follow geth semantics as in edge case 10.
22. **Size.** An unfiltered range on a busy chain can be many times larger than any filtered answer, which is why `maxRange` is small. A single height larger than `maxBlockBytes` is answered but not stored.
23. **Cross-replica fill lock.** With `connectorId` set and `peerWait > 0`, a replica's single fill for `(from, to)` first takes a Redis lock `<partition>:fill-lock/<from>-<to>` (`SET NX PX`, random token, TTL `min(fetchTimeout, 10s)`). The holder re-checks the store (a peer may just have finished), fetches, stores, then releases with a compare-and-delete script that only removes its own token. A replica that finds the lock held polls it every 50ms; releasing is the completion signal because the holder stores before it releases. When the lock disappears it reads the per-block entries: complete entries are served (`outcome="hit"`, `reason="peer_fill"`); any missing height (the peer hit the empty-tip guard, an oversized height, `unfinalizedTtl` expiry, or the peer's fetch failed) triggers an immediate local fetch without the lock, so near-tip waits end with the peer rather than at `peerWait`. If the lock is still held after `peerWait`, or any lock or poll Redis error occurs, the replica fetches locally without the lock. A request never fails because of the lock, and correctness never depends on the peer: a crashed holder costs at most `peerWait` of added latency until its lock expires.

24. **On-demand fetch, once fleet-wide.** A body miss for a window hash, or a logs miss for a single `blockHash` read or a `logs` subscription, reads Redis first, then fetches upstream once: concurrent misses on one replica share one call (singleflight per hash), and replicas coordinate through a Redis lock `<partition>:fill-lock/<kind>/<hash>` with the same mechanism, TTL and `logsFill.peerWait` bound as edge case 23. The result is validated against the window header and written to Redis keyed by `<kind>/<hash>` before the lock is released. A lock error or peer timeout falls back to a local fetch; a request never fails because of the lock. Per new block, the steady-state cost is one header on the lease holder (only while subscribers exist); each first full-block read adds one `eth_getBlockByNumber(n, true)`. `eth_getLogs` ranges are never expanded into per-block `blockHash` fetches (edge case 25).
25. **One logs path.** An explicit-range `eth_getLogs` is served by the live window only when every height's complete list is already held (adopted from a client's unfiltered range response or a `logsFill` fill); it never fetches per block hash. Otherwise, within `logsFill.maxRange` the request goes to `logsFill` (one unfiltered range call, stored per height, filtered locally), and wider ranges are forwarded unchanged as the client's own single call. The live window adopts each per-height list from those responses whose block hash matches a held header and that passes edge case 2 validation; heights whose header is not held are skipped (no header is fetched for them). Later window reads, `blockHash` reads and `logs` subscriptions for adopted blocks make no further logs calls.
26. **`logs` subscriptions trigger per-block logs.** While at least one `logs` subscription is open on a replica, each new block's logs are loaded once on that replica (Redis first, then one upstream fetch shared with HTTP misses and other replicas), for all its subscribers. `newHeads` never loads logs or bodies. With no `logs` subscribers nothing is fetched. A removed block's logs are re-emitted with `removed: true` from the cached entry; if they were never loaded, no `logs` subscriber was sent them, so nothing is retracted.
27. **Header following only with subscribers.** The lease-based header following (edge cases 3-5, 9) runs only while at least one WebSocket subscription exists somewhere in the fleet. A replica holding subscribers writes `<partition>:ws-presence` (value: the deadline in Unix ms) with TTL `3 × pollInterval` every tick; every replica reads it each tick, and a mark past its deadline counts as absent. A Redis error while following keeps following; it never starts following. When no subscriber remains (the mark expires), the lease is released and no replica fetches headers. The verified window and the last published snapshot are retained, so when a subscriber appears again following resumes from them (the 56d59790 handover/jitter rules apply) or from the chain clients already adopted (edge case 28), fetching only heights it lacks. A subscription opened while no verified view exists waits up to `leaseTTL + maxStaleness` (lease TTL is `max(3 × pollInterval, 2 × (fetchTimeout + pollInterval))`) for its first event, then closes; once it has received an event, normal gap rules (edge case 8) apply.
28. **Pull adoption from served responses.** Every successful `eth_getBlockByNumber`/`eth_getBlockByHash` (full or not) and `eth_getLogs` response a client receives through `Network.Forward`, served from the [EVM JSON-RPC cache](/config/database/evm-json-rpc-cache) or an upstream, is offered to the live blockstore asynchronously (at most 16 concurrent adoptions per network; excess is skipped). Directed requests (edge case 17's list) and the blockstore's own fetches are never adopted. Only heights above `latest - depth` (`latest` is the network's in-memory head, no upstream call) are held. A by-number or tag block result is canonical evidence at that time: its header (a full block is reduced to a hash-only header) is adopted, written to Redis as `header/<hash>`, and indexed as `canon/<n>` with its observation time so another replica can adopt it with no upstream call. A by-hash result only completes the body of a header already held. A full body is validated against the held header (edge case 2) and shared as `block/<hash>`. An `eth_getLogs` result marks each `(blockNumber, blockHash)` it carries as observed. Only an unfiltered result (no `address`/`topics`) over an explicit hex range within `maxLogsRange`, or an unfiltered `blockHash` result, is a complete per-block list. Each list is validated against its header and shared as `logs/<hash>`. A list whose header is not held is skipped: adoption never fetches a header, and the `blockHash` in the logs alone never authorizes storing a list. Filtered or tag-ranged results are never stored as complete. An adopted header is served while it, or a header linked above it by parent hash, was observed within `maxStaleness`, or for as long as it stays in the window once it was observed from an upstream response while its height was at or below the network's in-memory finalized height (finalized heights cannot reorg; responses replayed from the response cache and other replicas' index entries never qualify). Older unfinalized held heights become misses: the client's own request takes the normal path and its response is adopted. Adoption never makes an upstream call, so there are no link header fetches.
29. **Reorgs through adoption.** A fresh upstream observation of a different hash at a held height (a block header, or a log's `blockHash`) drops that entry, everything above it and their cached bodies/logs. Unfinalized entries below lose their confirmation until observed again, so they are not served on stale evidence. A header whose parent hash disagrees with the held height below it replaces that entry the same way. Older evidence than what is held never replaces it. Responses replayed from eRPC's response cache are weak evidence: they are adopted only where they conflict with nothing held, never confirm freshness, and never replace or drop held data, because an unfinalized cache entry can predate a reorg. A conflicting observation at a height of the followed snapshot marks it suspect, so the next tick re-verifies the tip.
30. **Blockstore fetches read through the response cache.** Header, body and logs fetches the blockstore makes (on demand, or subscriber-driven following) go through `Network.Forward` with the ordinary EVM JSON-RPC cache read and write enabled; only the blockstore itself is bypassed, so a fetch never recurses into it. They carry `IsInternal` (selects `matchRequestKind: internal` failsafe policies and skips the integrity pipeline and breaker accounting; it does not affect caching) and `RetryEmpty`. Empty results are never cached for not-yet-produced heights (`emptyResultBeyondConfidence`) and are not cached at all under the default `empty: ignore` policy. Unfinalized results use the cache's finality-aware TTLs. `logsFill`'s unfiltered range call keeps its own cache bypass (edge case 18).


## Observability

`erpc_blockstore_fresh{project,network}` is 1 when this process currently has a fresh verified live-window view, and 0 when it has no view or the view is stale. It is set after each refresh tick and cleared on stop. `erpc_blockstore_refresh_total{project,network,outcome}` counts live-window refresh ticks exactly once, with `outcome` equal to `fresh` when a fresh view exists, `stale` when no fresh view exists without a refresh error, or `error` when the refresh returned an error. `erpc_blockstore_hits_total{project,network,category}` counts requests served by the blockstore, live or historical, including a live read that first triggered its one on-demand fetch. `category` is one of `eth_getBlockByNumber`, `eth_getBlockByHash`, or `eth_getLogs`. These are per-process metrics; a fleet may therefore expose one freshness series per replica and network. Cache hits are marked `fromCache` and set `blockstore.hit=true` on the `Network.Forward` span. A `BlockStore.Tick` detail span records refresh errors when detailed tracing is enabled. Historical hits use the same hit counter; misses and normal upstream fallbacks do not increment it or change the live freshness/refresh metrics. With Redis fleet coordination, one lease holder performs live-window header polling per scope; independent EVM state pollers/probes still run per replica, and ordinary HTTP misses can still reach upstream.


`erpc_blockstore_fetch_total{project,network,kind,reason}` counts every upstream request the blockstore and `logsFill` initiate (blockstore fetches go through the response cache first, so a counted fetch may be answered by the cache). `kind` is `header`, `block`, `logs` or `head` (the `eth_blockNumber` fallback of header following). `reason` is `miss` (an HTTP read of a held block whose body, or a `blockHash` read whose logs, are not cached), `subscription` (subscriber-driven header following and its tip fallback, and a `logs` subscription's new block), or `fill` (`logsFill`'s one unfiltered range call, which answers the client's miss in its place). `background` is not emitted by eRPC's configuration. Adoption (live and historical) never fetches, so it has no reason here. With no clients and no WebSocket subscribers nothing grows. With subscribers, `kind="header",reason="subscription"` grows at one per new block per project scope (plus d per reorg of depth d, one retry per tick while the advertised tip is unavailable, and `maxPerTick` per tick during cold backfill). Tip jitter and a handover with available snapshot headers add no upstream header reads. Different projects retain independent leaders even for the same chain.

`erpc_blockstore_adopt_total{project,network,kind}` counts headers (`kind="header"`), full bodies (`block`) and complete log lists (`logs`) the live blockstore adopted from responses served to clients or from `logsFill`, with no fetch of its own. Adoptions from another replica's `canon/<n>` index are not counted.

`erpc_blockstore_logs_fill_total{project,network,outcome,reason}` counts logs-fill decisions per request. `outcome` is `hit` (all heights already stored), `fill` (served after one unfiltered upstream call), `fallback` (fill failed: `reason` is `fetch_error`, `parse_error`, `removed_logs`, `canceled` or `encode_error`; the original request is forwarded) or `skipped` (not eligible: `reason` is `params`, `not_explicit_range`, `invalid_range`, `filter`, `directive`, `limit`, `range_too_large`, `head_unknown` or `above_head`). `hit` and `fill` use `reason="ok"` except under the cross-replica lock (edge case 23): `hit` with `reason="peer_fill"` was served from another replica's fill; `fill` with `reason="peer_timeout"` (peer still holding after `peerWait`), `peer_incomplete` (peer released but some heights were not stored) or `lock_error` (Redis lock/poll error, fail-open) fetched locally after that coordination step. Served requests set `blockstore.logs_fill=true` on the `Network.Forward` span; `hit` responses are marked `fromCache`. The internal unfiltered call is a normal `eth_getLogs` in upstream request metrics.
