## Dependency notes

- Plan 001 is the **architecture + foundation**. It lands the `ConfigSource` /
  `ConfigController` / `Reloadable` contracts, static-mode parity, and one
  exemplar consumer. Follow-on work (upstream lifecycle, failsafe rebuild,
  auth strategy reload, docs page) should be separate plans once 001 proves
  the pattern — do not expand 001 into a full-tree rewrite.

## Findings considered and rejected

- **Simulator-style full `NewERPC` swap for production reload**: rejected as
  the primary model. Works for the toy process (`internal/simulator`) but
  breaks drain semantics for shared cache connectors, rate-limit Redis,
  metrics/HTTP listeners, and in-flight requests. Keep as last-resort only
  for restart-required fields.
- **Normalized SQL schema per config field**: rejected for v1. Reuse
  `data.Connector` (redis/postgres/dynamodb/memory) with a versioned JSON
  document — same pattern as DB auth keys. Normalized tables can be a later
  writer-side optimization without changing the controller contract.
- **File watch (`fsnotify`) as the dynamic path**: rejected as the product
  mode. Optional later sugar for local dev; the first-class dynamic mode is
  DB/connector-backed so multi-replica fleets share one source of truth.
