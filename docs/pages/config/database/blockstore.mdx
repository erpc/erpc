# Block store

Indexers, bots and dapps often poll the same few recent blocks with `eth_getLogs`, each
with its own `address`/`topics` filter, and every one of those calls normally reaches a
provider. With the block store on, eRPC fetches the complete logs of a small block range
once, keeps them per block, and answers every filter over those blocks locally.

- **On demand.** Nothing is polled in the background: a range is fetched only when a
  client asks for it and it is not already stored.
- **Safe fallback.** Anything the block store cannot answer exactly (tags, wide ranges,
  blocks above the head, odd filters, upstream errors) is forwarded unchanged, as if the
  feature were off.
- **Shared or local.** Point it at a Redis connector and replicas share entries and
  coordinate so only one of them fetches a given range. Without a connector each replica
  keeps a bounded in-memory store.

The tradeoff is response size: one unfiltered range on a busy chain can be much larger
than any filtered answer, which is why the handled range stays small (10 blocks by
default). Disabled by default; when disabled, behavior is unchanged.

## How it works

For an eligible `eth_getLogs` (see edge case 1), `Network.Forward` calls `tryServeLogsFill` before multiplexing and the ordinary JSON-RPC cache (<SourceLink file="erpc/networks.go" lines="1858-1865" />, <SourceLink file="erpc/logs_fill.go" lines="121-191" />). `LogsFiller.Serve` (<SourceLink file="blockstore/logsfill.go" />):

1. Reads one entry per height of `[fromBlock, toBlock]` from the store. Each entry is that block's complete, unfiltered log list (an empty list for blocks without logs) plus the id of the upstream response that produced it.
2. If every height is present and the entries are coherent (edge case 4), filters them locally and returns (`outcome="hit"`).
3. Otherwise makes one unfiltered `eth_getLogs{fromBlock,toBlock}` through the normal network path, splits it per height, stores the entries and answers from them (`outcome="fill"`). Concurrent misses of the same range coalesce (edge cases 5 and 6).
4. On any failure the client's original request is forwarded unchanged (`outcome="fallback"`).

## Config schema (`projects[].networks[].evm.blockStore`)

Defaults from `EvmBlockStoreConfig.SetDefaults` (<SourceLink file="common/config_blockstore.go" lines="50-77" />), called by `EvmNetworkConfig.SetDefaults` (<SourceLink file="common/defaults.go" lines="2570-2570" />). Bounds from `Validate` (<SourceLink file="common/config_blockstore.go" lines="79-108" />), which only runs when `enabled: true`.

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Opt-in. Disabled leaves every request on the normal path. |
| `connectorId` | empty | Optional id of a `driver: redis` connector in `database.evmJsonRpcCache.connectors`. Validated at config load (`ValidateConnector`); a missing or non-redis connector fails startup. Empty uses the per-replica in-memory store. |
| `namespace` | `default` | Isolation prefix for stored entries. The effective scope also includes a SHA-256 fingerprint of the network's upstream/provider set, upstream and network defaults, integrity config and network config, so config changes never read entries written under another trust set. |
| `maxRange` | `10` (1..1000) | Widest `toBlock - fromBlock + 1` handled. Further capped per request by `evm.getLogsMaxAllowedRange` and the smallest upstream `evm.getLogsAutoSplittingRangeThreshold`. |
| `finalizedTtl` | `1h` (> 0) | TTL of entries at or below the network's finalized height. |
| `unfinalizedTtl` | `0` = derived (>= 0) | TTL of entries above the finalized height. `0` uses the network's estimated block time clamped to 2s..12s, or 2s while unknown (<SourceLink file="erpc/logs_fill.go" lines="72-80" />). |
| `emptyTipGuard` | `2` (>= 1) | An unfinalized height with no logs is stored only when it is at least this many blocks below the network's latest head (sampled before the fetch). |
| `memoryMaxBytes` | `64MB` (>= 1MB) | Byte bound of the per-network in-memory LRU used when `connectorId` is empty. Ignored with a connector. |
| `peerWait` | `1.5s` (0..1m) | With `connectorId` only: the longest a miss waits for another replica already filling the same range. `0` disables cross-replica coordination (per-replica coalescing only). |
| `concurrency` | `4` (1..64) | Bounds simultaneous per-height store reads and writes for one request. |

Fixed limits (not configurable, <SourceLink file="erpc/logs_fill.go" lines="19-27" />): one fill (upstream call plus store writes) times out after `10s`, and a single height whose log list exceeds `16MB` is answered but not stored.

## Edge cases & gotchas

1. **Eligibility.** Only a single filter object with hex `fromBlock`/`toBlock` (no leading zeros, `to >= from`), optional `address`/`topics`, no `blockHash`, no other members, a span within the effective `maxRange`, and `toBlock` at or below the network's latest head is handled (<SourceLink file="erpc/logs_fill.go" lines="193-229" />). Tags (`latest`, `finalized`, …), an unknown head, split sub-requests and composite requests take the normal path untouched. Addresses must be 20-byte and topics 32-byte hex, otherwise the request goes upstream for normal validation (`TestHttp_LogsFill_MalformedFiltersBypass`).
2. **Network hard limits win.** A request exceeding `getLogsMaxAllowedRange`, `getLogsMaxAllowedAddresses` or `getLogsMaxAllowedTopics` is never answered locally; it reaches the normal path and gets the configured error (`exceedsGetLogsLimits`, <SourceLink file="erpc/blockstore_integration.go" lines="35-69" />, `TestHttp_LogsFill_HonorsNetworkHardLimits`).
3. **Directed requests bypass.** `useUpstream`, an integrity selector, internal requests, and any `skipCacheRead` value (including connector-ID patterns such as `redis-*`, because the block store sits in front of every connector) skip the block store with `reason="directive"`. An explicit `skipCacheRead: "false"` (any case) means no skip and is still served (`blockStoreDirected`, <SourceLink file="erpc/blockstore_integration.go" lines="21-34" />, `TestBlockStoreDirected_SkipCacheReadSemantics`).
4. **Reorg coherence.** Entries are keyed by height and overwritten by each fill, so a refill after a reorg replaces the old data. Every entry carries the id of the upstream response that filled it. A hit spanning unfinalized heights is served only when all of them came from one fill; entries from different fills may straddle a reorg (and an empty height carries no block hash to check), so the range is refilled instead. Finalized heights cannot reorg and may mix freely. Unfinalized entries live about one block time, bounding how long a reorged height can be served stale (`TestLogsFill_UnfinalizedHitRequiresOneFill`, `TestLogsFill_MixedPeerEntriesAreRefilled`).
5. **One upstream call per miss.** The fill is one unfiltered `eth_getLogs` for the whole requested range. Concurrent misses of the same `(from, to)` coalesce into one call per replica (singleflight); a cancelled first caller does not fail the others. The client's filtered request is never also sent upstream unless the fill fails (`TestHttp_LogsFill_ConcurrentRequestsCoalesce`).
6. **Cross-replica fill lock.** With `connectorId` and `peerWait > 0`, the replica first takes a Redis lock `<partition>:fill-lock/<from>-<to>` (`SET NX PX`, random token, TTL `10s`). The holder re-checks the store (a peer may just have finished), fetches, stores, then releases with a compare-and-delete that only removes its own token. Other replicas poll the lock every 50ms; release is the completion signal because the holder stores before it releases. Complete coherent entries are then served (`outcome="hit"`, `reason="peer_fill"`); any missing height (empty-tip guard, oversized height, expiry, failed peer fetch) triggers an immediate local fetch. A lock still held after `peerWait`, or any Redis lock/poll error, also falls back to a local fetch. A request never fails because of the lock (`TestHttp_LogsFill_ReplicasShareOneUpstreamCallViaRedis`, `TestLogsFill_LockErrorsFailOpen`).
7. **The fill fetch is internal.** It runs through normal selection, failsafe, retries and integrity with `IsInternal`, `SkipCacheRead` and `RetryEmpty` directives, so `matchRequestKind: internal` failsafe policies apply to it. It is never multiplexed with an identical client request, never served from the block store itself, and never written into the ordinary [EVM JSON-RPC cache](/config/database/evm-json-rpc-cache) (<SourceLink file="erpc/logs_fill.go" lines="82-115" />, `TestHttp_LogsFill_UnfilteredFetchIsInternal`, `TestHttp_LogsFill_InternalFetchNotMultiplexedWithClients`).
8. **Fallback never worsens behavior.** An upstream error, a null or non-array result, a log outside the range, two block hashes at one height, an invalid, negative or duplicate `logIndex`, or any `removed: true` log stores nothing and forwards the client's original request (`TestHttp_LogsFill_SkipsAndFallbacks`, `TestLogsFill_NegativeLogIndexRejected`).
9. **Empty tip heights.** A lagging upstream can report a block it has not imported yet as empty. Unfinalized empty heights within `emptyTipGuard` blocks of the head are answered but not stored.
10. **Response shape.** Results are the upstream's log objects byte-for-byte, ordered by block then `logIndex`; no match is `[]`, never `null`. Topic matching follows geth: a filter with more topic positions than a log never matches it, even when the extra positions are wildcards (`TestLogFilterGethSemantics`). `hit` responses are marked `fromCache`.
11. **Store errors are misses.** A Redis read error, a corrupt entry or an entry for the wrong height counts as a miss and triggers a fill; Redis write errors are ignored (`TestLogsFill_StoreErrorIsMiss`). Redis keys are `blockstore:v1:<sha256(scope)>:logs/<height>` with TTLs from `finalizedTtl`/`unfinalizedTtl`.
12. **Memory sizing.** `memoryMaxBytes` applies per enabled network per replica. Set Redis `maxmemory` and an eviction policy appropriate for the deployment when using a connector.
13. **Migrating from the nested `logsFill` key.** Earlier builds of this feature used `blockStore.logsFill.*` alongside live-window and historical keys (`depth`, `pollInterval`, `historical`, …). Those keys no longer exist: strict config decoding rejects them at load, so move `logsFill.*` fields up one level and set `blockStore.enabled: true` (`TestLoadConfig_BlockStoreFlatKeysRoundTrip`).

## Observability

`erpc_blockstore_logs_fill_total{project,network,outcome,reason}` (<SourceLink file="telemetry/metrics.go" />) counts one decision per eligible-method request:

| `outcome` | `reason` | Meaning |
|---|---|---|
| `hit` | `ok` | Every height already stored; answered locally. |
| `hit` | `peer_fill` | Served from another replica's fill after waiting on its lock. |
| `fill` | `ok` | Served after one unfiltered upstream call. |
| `fill` | `peer_timeout`, `peer_incomplete`, `lock_error` | Fetched locally after cross-replica coordination: peer still held the lock after `peerWait`, peer released without storing every height, or a Redis lock/poll error. |
| `fallback` | `fetch_error`, `parse_error`, `removed_logs`, `canceled`, `encode_error` | The fill failed; the original request was forwarded. |
| `skipped` | `params`, `not_explicit_range`, `invalid_range`, `filter`, `directive`, `limit`, `range_too_large`, `head_unknown`, `above_head` | Not eligible; forwarded unchanged. |

Served requests set `blockstore.logs_fill=true` on the `Network.Forward` span. The internal unfiltered call appears as a normal `eth_getLogs` in upstream request metrics.
