# WebSocket

eRPC supports WebSocket connections on the same HTTP port. Clients can connect via `ws://` or `wss://` for persistent JSON-RPC connections and real-time subscriptions (`eth_subscribe`). The server side is **off by default**: set `server.webSocket.enabled: true` to accept connections.

## Connecting

Connect to eRPC using the same URL path as HTTP, but with the `ws://` or `wss://` scheme:

```
ws://<your-erpc-hostname>/<project-id>/<network-architecture>/<chain-id>
```

```javascript
// Browser / Node.js example
const ws = new WebSocket("ws://localhost:4000/main/evm/1");

ws.onopen = () => {
  ws.send(JSON.stringify({
    jsonrpc: "2.0",
    id: 1,
    method: "eth_blockNumber",
    params: []
  }));
};

ws.onmessage = (event) => {
  console.log(JSON.parse(event.data));
  // { "jsonrpc": "2.0", "id": 1, "result": "0x1234567" }
};
```

<Callout type="info">
  WebSocket connections use the same port as HTTP once `server.webSocket.enabled` is `true`. With it off, an upgrade request is answered as ordinary HTTP. Domain aliasing rules also apply to WebSocket connections.
</Callout>

## Regular JSON-RPC over WebSocket

All JSON-RPC methods supported over HTTP also work over WebSocket. The connection is persistent, so you can send multiple requests without reconnecting:

```javascript
// Send multiple requests on the same connection
ws.send(JSON.stringify({ jsonrpc: "2.0", id: 1, method: "eth_blockNumber", params: [] }));
ws.send(JSON.stringify({ jsonrpc: "2.0", id: 2, method: "eth_chainId", params: [] }));
ws.send(JSON.stringify({ jsonrpc: "2.0", id: 3, method: "eth_getBlockByNumber", params: ["latest", false] }));
```

Batch requests (JSON arrays) are also supported:

```javascript
ws.send(JSON.stringify([
  { jsonrpc: "2.0", id: 1, method: "eth_blockNumber", params: [] },
  { jsonrpc: "2.0", id: 2, method: "eth_chainId", params: [] }
]));
// Response is a JSON array
```

All eRPC features work identically for WebSocket RPC requests: authentication, method filters, caching, upstream scoring, failsafe policies (retry, hedge, circuit breaker), rate limiting, multiplexing (request deduplication), EVM integrity checks, and metrics. Each request is bounded by `server.maxTimeout`, and a connection processes at most `server.webSocket.maxConcurrentRequestsPerConnection` messages at once — further messages wait until one finishes. A batch is one message; its requests run concurrently, as over HTTP. Credentials (`secret` query parameter or headers, JWT, SIWE, client IP) come from the upgrade request: an upgrade that no auth strategy accepts is refused with `401`, and each request on the connection is still authenticated, with method scoping and rate limits, as over HTTP.

## Subscriptions

eRPC supports `eth_subscribe` and `eth_unsubscribe` for real-time event streaming. Subscriptions require at least one upstream configured with a `ws://` or `wss://` endpoint.

### eth_subscribe

```javascript
const ws = new WebSocket("ws://localhost:4000/main/evm/1");

ws.onopen = () => {
  // Subscribe to new block headers
  ws.send(JSON.stringify({
    jsonrpc: "2.0",
    id: 1,
    method: "eth_subscribe",
    params: ["newHeads"]
  }));
};

ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  
  if (msg.id) {
    // Subscription confirmation
    console.log("Subscription ID:", msg.result);
    // "0x2a151383161618ebffddfed9de4be5db"
  }
  
  if (msg.method === "eth_subscription") {
    // New block notification
    console.log("New block:", msg.params.result.number);
  }
};
```

Supported subscription types (depends on upstream node capabilities):
- `newHeads` — new block headers
- `logs` — log entries matching a filter
- `newPendingTransactions` — pending transaction hashes

#### Subscribing to logs with a filter

The second params entry is a filter object with optional `address` (string or array) and `topics` (array of topic hex strings or arrays for OR-matching). The filter is hashed by eRPC so multiple clients requesting the same filter share a single underlying upstream subscription.

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "eth_subscribe",
  params: [
    "logs",
    {
      address: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48", // USDC
      topics: [
        "0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef" // Transfer
      ]
    }
  ]
}));
```

### eth_unsubscribe

```javascript
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 2,
  method: "eth_unsubscribe",
  params: ["0x2a151383161618ebffddfed9de4be5db"]
}));
// Response: { "jsonrpc": "2.0", "id": 2, "result": true }
```

### Subscription features

- **Resilient delivery** — `newHeads` is subscribed on every connected WebSocket upstream of the network, and each block is delivered from whichever upstream announces it first. With [`failover.onDefaultsExhausted`](/config/projects/networks#failover) enabled, heads from upstreams tagged `tier:fallback` are delivered only while no other upstream that the selection policy routes to has a live `newHeads` subscription, so clients are not told of a block only a fallback has while the primaries are up. A held-back head still updates that fallback's tip tracker. How quickly fallback heads take over when the primaries fail follows the selection policy's `evalInterval`. `newPendingTransactions` is subscribed on every WebSocket upstream; with [`failover.onDefaultsExhausted`](/config/projects/networks#failover) enabled, on every one outside `tier:fallback` that the selection policy routes to, and on the `tier:fallback` upstreams only while none of those has the subscription live. This is rechecked on every head, so the fallbacks take over when the primaries drop a subscription (or the policy excludes them) and hand it back once a primary has it live again; a subscribe that fails is retried in the background.
- **No surprise disconnects** — upstream reconnects, scoring changes and brief outages never close your connection; eRPC re-subscribes upstream behind the scenes. eRPC closes a connection only on shutdown (`1001`), when the client stops answering pings, or with `1013` when a `logs` subscription cannot continue (see below).
- **Deduplication** — even though multiple upstreams are subscribed in parallel, you only receive each block or pending tx once.
- **Shared subscriptions** — clients subscribing to the same event on the same network share one upstream subscription per upstream. Each client gets its own subscription ID and receives every notification independently.
- **Slow-client safety** — a slow reader never blocks other clients or upstream delivery. A `logs` subscription more than `chainTracker.reorgWindow` blocks behind closes the connection with `1013`, so the client knows it may have missed logs and can re-subscribe and backfill with `eth_getLogs`.
- **Connection-scoped IDs** — eRPC issues its own subscription IDs, so they stay the same across upstream reconnects and upstream switches. They belong to the connection that created them: `eth_unsubscribe` only works on that connection, and subscriptions end when it closes.
- **Rate limiting** — subscribe/unsubscribe calls count against the same project and network rate limits as regular RPC.

### `logs` subscriptions

eRPC builds `logs` notifications from each block's `eth_getBlockReceipts`, fetched once per block when the block's `logsBloom` may match a subscribed filter; no upstream `logs` subscription is made. The filter takes `address` and `topics` as geth does; `fromBlock` and `toBlock` are ignored. A filter that does not parse fails with `-32602`.

When a reorg drops a block with matched logs, eRPC sends those logs again with `"removed": true`, newest first, then the logs of the new branch. A block whose receipts no upstream serves for 60s closes the connections of its `logs` subscriptions with `1013`, spread over 60s.

```javascript
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.method === "eth_subscription" && msg.params.result.removed) {
    // This log was in a block that was reorged out.
    // Roll back any state you derived from it.
  }
};
```

### When eth_subscribe fails

`eth_subscribe` returns a JSON-RPC error when:

- the network has no subscription source for the type; for `logs`, no upstream serves `eth_getBlockReceipts` (or `eth_getLogs` with integrity off), or every such fetch has failed for 60s;
- the subscription type is not supported, or a `logs` filter does not parse (`-32602`);
- the connection already has `server.webSocket.maxSubscriptionsPerConnection` active subscriptions (`-32005`);
- the instance already has `server.webSocket.maxSubscriptions` active subscriptions (`-32005`);
- the request is rate limited.

A failed `eth_subscribe` leaves your WebSocket connection open. You can retry on the same connection.

## WebSocket upstreams

To support subscriptions, configure at least one upstream with a `ws://` or `wss://` endpoint:

<Callout type="info">
  WebSocket upstreams also serve regular JSON-RPC requests (not just subscriptions). eRPC's scoring system picks the best upstream regardless of transport — HTTP or WebSocket.
</Callout>

The WebSocket upstream client features:
- **Persistent connection** with automatic reconnection — every re-dial waits a jittered exponential backoff (1s to 30s), which resets only after a connection has stayed up for a full keepalive window
- **Ping/pong keepalive** (30s interval) to detect dead connections
- **Lazy connection** — if the upstream is unavailable at startup, eRPC retries in the background without blocking
- **Fail-fast while reconnecting** — requests sent while the connection is down fail immediately with a retryable error so they fail over to other upstreams
- **Heads subscribed at startup** — while the WebSocket server is enabled, eRPC subscribes to `newHeads` on every WebSocket upstream as soon as its network initializes, so state pollers use pushed heads instead of polling even before any client subscribes
- **Silent subscription recovery** — if a `newHeads` subscription stops delivering while the same upstream's polled head keeps advancing, eRPC reconnects to that upstream
- **Unsupported `newHeads` is not retried** — if an upstream rejects `eth_subscribe newHeads` as unsupported, eRPC stops asking until the next reconnect or resubscribe; its state poller keeps tracking the head

`eth_subscribe` and `eth_unsubscribe` are only sent to upstreams by eRPC's own subscription handling. Over HTTP both are rejected with `-32601` without reaching any upstream, since a subscription needs a client WebSocket connection to deliver to.

## Server configuration

The WebSocket server is enabled and tuned via the `webSocket` section in server config. Only `enabled` is required; the other defaults work well for most deployments. WebSocket upstreams (`ws://` / `wss://` endpoints) work regardless of this setting.

```yaml filename="erpc.yaml"
server:
  httpPortV4: 4000
  webSocket:
    # Accept WebSocket upgrades on the HTTP port (default: false)
    enabled: true
    # Read buffer size in bytes (default: 4096)
    readBufferSize: 4096
    # Write buffer size in bytes (default: 4096)
    writeBufferSize: 4096
    # Maximum incoming message size in bytes (default: 1048576 = 1MB)
    maxMessageSize: 1048576
    # Ping interval for keepalive (default: 30s). A client that sends neither
    # a pong nor a request within twice this interval is disconnected.
    pingInterval: 30s
    # Maximum active subscriptions per WebSocket connection (default: 100)
    maxSubscriptionsPerConnection: 100
    # Maximum requests a connection runs at once (default: 250)
    maxConcurrentRequestsPerConnection: 250
    # Notifications queued per subscription for a slow reader (default: 256)
    subscriptionBufferSize: 256
    # Instance-wide caps; 0 (the default) means unlimited
    maxConnections: 0
    maxConnectionsPerIP: 0
    maxSubscriptions: 0
```

`maxSubscriptionsPerConnection` alone does not bound a client: it can open any number of connections. On a public endpoint also set the instance-wide caps:

- `maxConnections` — concurrent client connections on the instance. The only connection cap that holds when client IPs are unknown or spoofed.
- `maxConnectionsPerIP` — concurrent client connections from one client IP, resolved as for HTTP (see `trustedIPForwarders`). Together with `maxSubscriptionsPerConnection` it bounds one client's subscriptions.
- `maxSubscriptions` — active subscriptions across all connections on the instance.

A connection over a cap is refused with `429` before the upgrade; a subscription over `maxSubscriptions` gets a JSON-RPC error and the connection stays open. Refusals are counted in `erpc_websocket_rejected_total`. The caps are per instance, so a fleet admits up to N times each.

The upgrade request must name a network (`/<project-id>/<architecture>/<chain-id>`, or a path that [domain aliasing](/operation/url) resolves to one); otherwise it is rejected with `400`. On shutdown eRPC closes every client connection with `1001` (going away) straight away so clients reconnect to another instance; in-flight requests get up to `server.waitBeforeShutdown` to answer first.

## Cost frames

A metering proxy in front of eRPC can read per-message cost the way it reads HTTP [cost headers](/operation/directives) (`server.costHeaders`). Opt in per connection by sending `X-ERPC-Cost-Frames: 1` on the upgrade request; it takes effect only while `server.costHeaders` is `true`. Otherwise output is plain JSON, as above.

In cost-frame mode **every** text message eRPC sends starts with a header block in HTTP/1.1 wire form — zero or more `Name: value\r\n` lines, then `\r\n` — followed by the unchanged JSON body, all in one WebSocket message:

```
X-Erpc-Billable: 1\r\n
X-Erpc-Calls: 1\r\n
X-Erpc-Methods: eth_blockNumber\r\n
X-Erpc-Network-Alias: ethereum\r\n
X-Erpc-Network-Id: evm:1\r\n
\r\n
{"jsonrpc":"2.0","id":1,"result":"0x1234567"}
```

- **Responses** (single and batch) carry exactly the cost headers the same calls would get over HTTP (`X-ERPC-Calls`, `X-ERPC-Billable`, `X-ERPC-Methods`, `X-ERPC-Credits`, `X-ERPC-Credits-Total`, `X-ERPC-Credits-Version`, `X-ERPC-Network-Id`, `X-ERPC-Network-Alias`). A batch's `X-ERPC-Calls` counts every request in it, including id-less requests (JSON-RPC notifications) that get no reply entry.
- **Calls that get no reply** — an id-less request, or a batch of only those — still ran, so they get a *metering-only* message: the header block for those calls followed by an empty body. A proxy meters it and never relays it.
- **Messages that routed no call** — a batch that is not valid JSON, an empty batch — start with just `\r\n`.
- **Subscription notifications** (`eth_subscription`) each carry `X-ERPC-Calls: 1`, `X-ERPC-Billable: 1`, `X-ERPC-Methods: eth_subscription`, `X-ERPC-Subscription: <newHeads|logs|newPendingTransactions>`, `X-ERPC-Network-Id` and `X-ERPC-Network-Alias`; no credits.

Header names are case-insensitive, as in HTTP. Cost frames are not valid JSON-RPC: only send the header from a proxy that strips the block before the client sees the message.

## Subscription compatibility knobs

### HTTP / WebSocket tip-sync considerations for strict consumers

Some RPC consumers compare the block number returned by HTTP `eth_getBlockByNumber("latest")` against a tip they've observed via a WebSocket `newHeads` subscription and flag any lag as a health-check failure. On fast-block chains (sub-second to a few seconds) the HTTP round-trip can trivially exceed the inter-block interval, so the HTTP response carries a block that was current when it was generated but older than a `newHeads` notification that arrived in parallel. That behaviour is inherent to HTTP-vs-push timing and is visible with or without a proxy in front.

eRPC minimises the gap in three ways:

- **Per-block cache keying for moving tags.** The realtime cache entry for a `latest` / `finalized` request is keyed by the block number the tag currently resolves to, so each tip advance is a distinct key rather than pinning every call within the TTL to the same cached payload.
- **`enforceHighestBlock` response rewrite.** When the upstream returns a block number below the network's tracked tip, eRPC's [integrity check](/config/failsafe/integrity) fetches the specific higher block from another upstream and returns that instead (falling back to the highest valid block it has if none can serve it).
- **Delivered-head floor.** When an upstream WebSocket delivers a `newHeads` notification, eRPC updates that upstream's tip tracker before fanning the head out to clients, and records it as a floor for the network's `latest`. A head reaches subscribers, and feeds the floor, only once the delivering upstream's tip tracker has accepted it; a head far ahead of the tracker is verified first and is not delivered, so subscribers resume with the next head. Held-back fallback heads are not delivered either. With shared state configured the floor is also propagated to other instances in the background, so they converge within the propagation delay rather than instantly. How the floor bounds and orders against the served tip: [Block tracking](/reference/evm/block-tracking#websocket-delivered-head-floor).

Even so, a transient single-block lag can reach a client when the chain produces a block faster than an in-flight HTTP round-trip completes. If your consumer treats single-block HTTP-vs-WS lag as a hard failure, widen its tolerance to match the chain's block time rather than expect eRPC (or any proxy) to eliminate it.

## Directives

[Request directives](/operation/directives) can be set via headers or query parameters on the initial WebSocket upgrade request. They apply to every regular RPC request on that connection, batches included, subject to the same `allowClientDirectives` rules as HTTP:

```javascript
// Pass directives via query params on the WebSocket URL
const ws = new WebSocket("ws://localhost:4000/main/evm/1?useUpstream=my-preferred-upstream");
```

Subscriptions (`eth_subscribe`) ignore the `useUpstream` directive — they're delivered by the network's WebSocket upstreams as described above, so notifications keep flowing if any upstream slows down.
